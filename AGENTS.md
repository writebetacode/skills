- New feature or fix: its own branch (`branch` skill) before the first edit.
- Asking the user anything: `same-page`, one question per reply.
- LLM-directed text (skills, agents, prompts, this file): as terse as possible; each fact in one place, except a rule every call needs: mechanical → one skill script they all run; else a copy per skill (`SHARED` in `free_checks.py` keeps the copies identical). Human docs: `voice` skill.
- After writing any `.md`: `npx markdownlint-cli2@0.23.3 --fix <file>`, then fix remaining errors.
- Changing a skill: first make its `evals/<skill>/` cases match any added, changed or removed behavior. Then `python3 evals/check.py --free --reviewed`; fix each ✗. Over a word budget → cut; raise the budget only once the user OKs it.
- Before each commit: re-read every changed file whole; grep the repo for each name, term and behavior you changed (skills, agents, evals, README, this file, docstrings) and update every stale mention. Passing evals don't check docs.
- Paid evals (`python3 evals/check.py <model> <changed|since-release|skill,…|all>`; slow, costs tokens): only when the user asks (default `changed`), or before `release` cuts a version here (`since-release`; `all` when your model has no `evals/scores.json` baseline and is stronger than every model that does: Opus 5.5 → Opus 6 yes; → Sonnet 6 only if it's actually stronger). A `~` flaky line → fix the grader or skill it names. Model: yours unless the user names one. Runs: the default 3 per case; more only when the user asks. No ▼ → `python3 evals/check.py --accept`; ▼ → fix the skill, or accept once the user OKs it.
- Adding, removing, renaming or changing what a skill does: update its README section (`### wbc:<skill>` under the `## <group> skills` it fits, each group preceded by `---`; `voice`, 1–2 sentences: why you'd use it, then what it does; internal-only → say so). Skills live in `skills/<name>/`.
- Agents: `agents/<name>.md`, flat (a subfolder joins the name: `wbc:<folder>:<name>`); called only by skills. Changing one = changing each skill that names it.
- New kind of file or convention: add its rule here, and make `free_checks.py` and `check.py` cover it (links, budgets, `changed`).
- A skill writing files into the repo it works on: under `<git rev-parse --show-toplevel>/.ai/<area>/`; ensure `.ai/.gitignore` holds `*` (ignores all of `.ai/` in that clone only). Only files meant to be committed go elsewhere (`plan`'s approved specs: `docs/specs/`). Never `.claude/` or `.git/`: Claude Code protects them, so every write prompts or is denied.
- Skill scripts: `skills/<name>/<script>`, executable, run as `${CLAUDE_SKILL_DIR}/<script>` (another skill's: `${CLAUDE_SKILL_DIR}/../<name>/<script>`; sibling `.md` files get no substitution: `<this skill's base directory>/../<name>/<script>`); shell that runs on macOS (BSD) and GNU tools alike.
- `check.py` asks for a user review of the diff: pre-approved; add `--reviewed` without asking.
- Cases: only those needed, at most 3 per skill plus 1 per sibling file a case exists to cover (`land.md`, a host table); never pad. Each pins a behavior Claude wouldn't show by default, or a skill not firing where it shouldn't; `tags`: the skill plus every skill the case invokes; free graders only (`regex`, `tool_used`, `tool_order`, `file_exists`); a grader requiring a skill or agent to fire: name ends `-fired` (Δ leaves it out); copy an existing case's shape; git remote, `gh`, `glab` or `acli` → `evals/lib/setup.sh`. `file_exists` sees only files the run created or changed: check fixture-made files with `regex`.
- Case env: only `EVAL_*` keys. Evals don't load a fixture's `CLAUDE.md`: put what it would say in `append_system_prompt`. A trace grader on a command: `"command":\s*"(?:[^"\\]|\\.)*?(?:\\n|\b)<cmd>` (the trace is JSON: a quoted arg reads `\"`, a later line `\n<cmd>`); `free_checks.py` flags the rest.
- Cases stay unit-test quick; a slow multi-step flow (e.g. PR → merge → tag → release) goes untested, left to real use, unless the user asks for a test.
- New case: at the next paid run, also `--case <name> --with-without`; Δ ≤ 0 → it pins nothing, unless it checks a skill not firing (grade that `arm: both`).
