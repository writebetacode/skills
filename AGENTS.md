- New feature or fix: its own branch (`branch` skill) before the first edit.
- Asking the user anything: `same-page`, one question per reply.
- LLM-directed text (skills, agents, prompts, this file): as terse as possible; each fact in one place, except a rule every call needs: mechanical → one `bin/` script they all run; else an identical copy per skill. Human docs: `voice` skill.
- Every skill but `voice`: `VOICE_LINE` from `scripts/check.py`, word for word, as its `SKILL.md`'s first body line (it checks); no `voice` step of its own. Tone rules live only in `voice`.
- After writing any `.md`: `bin/lint-md.sh <file>`, then fix what it prints.
- A skill writing or editing `.md` files in a repo (`.ai/` included): `plan`'s `lint-md.sh` line (siblings: `<this skill's base directory>/../../bin/lint-md.sh`); `build`'s covers only the plan folder and spec folders, leaving a repo's other docs to its own linter. Never a file outside a repo (`daily`'s notes, `~/.claude/CLAUDE.md`): `--fix` would rewrite the user's own lines. Templates lint clean as written: `scripts/check.py` lints them.
- Changing a skill or `docs/proposed-improvements.md`: `python3 scripts/check.py`; fix each ✗. Over a word budget → cut; raise the budget only once the user OKs it.
- Before each commit: re-read every changed file whole; grep the repo for each name, term and behavior you changed (skills, agents, scripts, README, this file, docstrings) and update every stale mention.
- Adding, removing, renaming or changing what a skill does: update its README section (`### wbc:<skill>` under the `## <group> skills` it fits, each group preceded by `---`; `voice`, 1–2 sentences: why you'd use it, then what it does; internal-only → say so), and `## How they fit together` and `## What waits for you` where they name it. Skills live in `skills/<name>/`.
- A repo's specs: in the folders `bin/specs-dir.sh` prints; skills and agents never name `docs/specs` (`scripts/check.py` checks). Ticket titles and bodies, `plan`'s ticket files included: only `skills/ticket/templates.md`.
- Agents: `agents/<name>.md`, flat (a subfolder joins the name: `wbc:<folder>:<name>`); called only by skills; only to check another's work in a fresh context, else a skill file (parallel reading: built-in `Explore`). Changing one = changing each skill that names it.
- New kind of file or convention: add its rule here, and make `scripts/check.py` check it where it can (links, budgets).
- Ideas for skills, agents or features: `docs/proposed-improvements.md` (human doc). Read it before proposing one; never propose a `Rejected` idea again. Add each new idea with the user's verdict as its status, a skill or agent's Idea cell starting `` `wbc:<name>` `` (the check matches only that); the PR that ships one deletes its row.
- A skill writing files into the repo it works on: under the folder `bin/ai-dir.sh --write <area>` prints (the main checkout's `.ai/<area>/`, shared by every worktree; it keeps `.ai/.gitignore` holding `*`); a lookup drops `--write`. A folder's repo: `bin/main-checkout.sh`. Each skill writing into a main checkout carries `plan`'s line for a refused Edit/Write, word for word (`setup`'s: `CLAUDE.local.md`, no folder or `ai-dir.sh` step). Only files meant to be committed go elsewhere (the specs `build` commits into the repo's spec folder), plus `setup`'s gitignored `CLAUDE.local.md` in each repo's main checkout. Never `.claude/` or `.git/`: Claude Code protects them, so every write prompts or is denied.
- Scripts, executable, shell that runs on macOS (BSD) and GNU tools alike: one skill's in `skills/<name>/`, run as `${CLAUDE_SKILL_DIR}/<script>` (sibling `.md` files get no substitution: `<this skill's base directory>/<script>`); run by more than one skill → `bin/`, run as `${CLAUDE_PLUGIN_ROOT}/bin/<script>` (siblings: `<this skill's base directory>/../../bin/<script>`; a skill's script: `$(dirname "$0")/../../bin/<script>`; another `bin/` script: `$(dirname "$0")/<script>`). Never run a script from another skill's folder.
