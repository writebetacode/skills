- LLM-directed text (skills, agents, prompts, this file): as terse as possible; each fact in one place. Human docs: succinct.
- After writing any `.md`: `npx markdownlint-cli2@0.23.3 --fix <file>`, then fix remaining errors.
- Changing a skill: first make its `evals/<skill>/` cases match any added, changed or removed behavior. Then `python3 evals/check.py <model> <skill>` (model: yours unless the user names one; `all` instead of `<skill>` after changing `evals/check.py`). No ▼ → `python3 evals/check.py --accept`; ▼ → fix the skill, or accept once the user OKs it.
- Adding, removing, renaming or changing what a skill does: update its README section (`#### wbc:<skill>` under its folder's `###`; 1–2 sentences: what it does, why you'd call it; internal-only → say so). New skill folder → also its `###` and a `skills` entry in `.claude-plugin/plugin.json`.
- A skill writing files into the repo it works on: under `<git rev-parse --show-toplevel>/.ai/<area>/`; ensure `.ai/.gitignore` holds `*` (ignores all of `.ai/` in that clone only). Never `.claude/` or `.git/`: Claude Code protects them, so every write prompts or is denied.
- `check.py` asks for a user review of the diff: pre-approved; add `--reviewed` without asking.
- Cases: 1–3 per skill, each pinning a behavior Claude wouldn't show by default, or a skill not firing where it shouldn't; `tags`: the skill plus every skill the case invokes; free graders only (`regex`, `tool_used`, `tool_order`, `file_exists`); copy an existing case's shape; git remote or `gh` → `evals/lib/setup.sh`. `file_exists` sees only files the run created or changed: check fixture-made files with `regex`.
- Cases stay unit-test quick; a slow multi-step flow (e.g. PR → merge → tag → release) goes untested, left to real use, unless the user asks for a test.
- New case: also run check.py with `--case <name> --with-without`; Δ ≤ 0 → it pins nothing, unless it checks a skill not firing (grade that `arm: both`).
